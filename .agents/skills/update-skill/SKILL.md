# 创建或更新 Skill

创建新的 Skill，或在保留现有意图和调用约定的前提下改进已有 Skill。先读取目标仓库的规则与相邻 Skill，再决定需要哪些文件；不要把某个 Agent 的安装目录或专属工具硬编码进通用源码。

## 基本结构

每个 Skill 都是一个目录，其中只有 `SKILL.md` 必需：

```text
skill-name/
├── SKILL.md
├── agents/               # 可选的宿主 UI 元数据
│   └── openai.yaml
├── scripts/              # 可选的确定性辅助脚本
├── references/           # 可选的按需参考资料
└── assets/               # 可选的输出素材或模板
```

不要创建空目录、占位文件、Skill 内 README、安装指南或变更日志，除非目标仓库或用户明确要求。

## frontmatter

`SKILL.md` 必须以 YAML frontmatter 开头：

```markdown
---
name: pdf-processing
description: "从 PDF 提取文本和表格、填写表单并合并文档。适用于处理 PDF、表单或文档提取任务。"
---

# PDF 处理
```

- `name`：使用小写字母、数字和连字符，且与目录名一致。
- `description`：同时说明“做什么”和“何时使用”，加入真正影响发现的关键词。
- 直接描述动作，不写“我可以帮你”或“你可以用它”。
- 当相邻能力容易误触发时，补充一条有意义的排除边界；不要罗列所有不适用场景。

描述决定 Skill 是否会被加载。避免“帮助处理代码”“执行开发任务”等无法区分用途的表述。更多规则见 [references/best-practices.md](references/best-practices.md#编写有效描述)。

## 工作流

1. **确定范围。** 查找目标目录、仓库规则、Skill 清单和已有同名或相邻 Skill。确认是新增、局部修订还是结构调整。
2. **先读后写。** 更新已有 Skill 时，读取 `SKILL.md` 及其直接引用的资源；在删除或移动资源前查清调用方。
3. **选择最小结构。** 简单 Skill 保持单文件；只有可独立按需加载的详细内容才进入 `references/`，重复且需要确定执行的逻辑才进入 `scripts/`。
4. **编写指令。** 保留用户选择、授权边界和真实运行约束。删除常识、重复说明、推测性规则和没有决策价值的示例。
5. **同步发现入口。** 仅更新目标仓库实际使用的清单、目录树或 UI 元数据；不要在源码仓库创建各 Agent 的安装目录、软链接或安装脚本。
6. **验证。** 运行仓库已有的 Skill 校验器；再检查引用文件可达、描述能准确触发、脚本可执行且没有遗留占位内容。

## 内容组织

- 简单 Skill 通常只需要标题和直接指令。
- 工作流只有在顺序会影响结果时才使用编号步骤。
- `SKILL.md` 接近 150 至 200 行，或包含多个可独立加载的领域时，把详细内容拆到 `references/`。
- 所有参考文件应由 `SKILL.md` 直接链接。避免多层引用；超过 100 行的参考文件应提供目录。
- 代码块始终标注语言。命令给出完整参数，只解释不明显且确实影响行为的选项。

详细写作、组织、示例和反模式见 [references/best-practices.md](references/best-practices.md)。

## 验证清单

- `SKILL.md` 首行是 `---`，frontmatter 可以解析。
- `name` 符合 kebab-case 且与目录名一致。
- `description` 非空、可区分，并同时包含能力和触发场景。
- 正文没有 `TODO`、模板占位符、无效链接或未闭合代码围栏。
- 每个 `references/` 文件都能从 `SKILL.md` 找到入口。
- 新增或修改的脚本已按真实用途运行；仅文档变更不以构建代替内容检查。
- 仓库清单和 UI 元数据与最终 Skill 行为一致。
- 暂存、提交、安装或发布只在用户明确要求时执行。

若仓库没有可用校验器，不要为了验证擅自安装依赖。改用无依赖结构检查，并在结果中说明未运行的官方校验及原因。
