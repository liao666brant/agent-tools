# Code Review

对同一份变更分别完成两条独立审查轴：

- **规范（Standards）**：变更是否违反仓库已记录的约定，或引入明显的设计坏味道。
- **需求（Spec）**：变更是否完整、正确且不过度地实现了可获得的需求说明。

本技能是自包含且只读的：不要要求、安装或调用其他 skill、子代理、issue tracker 配置或特定 agent 的专属能力。只使用当前环境已有的 Git、文件读取、搜索和诊断能力。始终只报告问题和最小修复方向，不修改文件、不暂存、不提交；用户要求修复时，将修复作为审查结束后的独立任务处理。

## 确定审查范围

将用户提供的 commit SHA、分支名、tag、`main` 或 `HEAD~N` 作为固定点，并将其视为不可信输入。不要把原始值拼接进 shell 命令；通过宿主提供的参数边界或已引用变量将它作为单个参数传递。先解析为 commit SHA，后续命令只使用解析结果。下面的 `$fixed_point` 表示已由宿主安全赋值的单个参数：

```bash
base_commit="$(git rev-parse --verify --end-of-options "${fixed_point}^{commit}")"
git log --oneline "${base_commit}..HEAD" --
git diff --check "${base_commit}...HEAD" --
git diff --find-renames "${base_commit}...HEAD" --
```

三点 diff 自动以固定点和 `HEAD` 的共同祖先为基准，适合分支或 PR 审查。固定点解析失败或 diff 为空时立即说明，且不要臆造审查结果。

用户未给固定点时，默认审查当前未提交改动，不猜测 `main`、远程跟踪分支或某个 PR。先记录并审查已跟踪文件的最终工作树状态：

```bash
git status --short
git diff --check HEAD
git diff --find-renames HEAD
git ls-files --others --exclude-standard -z
```

`git diff HEAD` 同时覆盖已暂存与未暂存的已跟踪变更。逐个将非忽略的未跟踪文件作为新增内容读取，并用等价的 no-index diff 审查：

```bash
git diff --no-index --check -- /dev/null "$review_file"
git diff --no-index -- /dev/null "$review_file"
```

`--no-index` 发现内容差异时返回 1 是正常结果，不代表命令执行失败；用 `--check` 的诊断内容判断空白错误。文件路径必须作为已引用的单个参数传递。若已跟踪与未跟踪变更均为空，说明没有可审查的未提交改动。用户明确指定固定点时，始终改用该固定点的三点 diff。

## 收集证据

先读完整 diff，以及存在固定点时的提交列表，再按需要读取受影响文件的上下文、调用方、测试和配置。不要只凭 diff 中的一行推断行为。

按以下优先级寻找需求来源：

1. 用户直接提供的需求文本、路径或链接；
2. 提交信息中指向的本地 issue、设计或需求文件；
3. `docs/`、`specs/`、`.scratch/` 及与分支或功能名称相符的本地文档。

链接只在当前环境已有能力可以直接读取时使用；不要为此安装或配置工具、登录服务或绕过访问限制。只把实际读取到的内容当作需求证据。仅有 `#123`、`!67` 等编号或链接内容不可用时，不能据此推测需求；将 Spec 轴标记为“无可用需求说明”。

再查找仓库规范来源，例如根或相关目录的 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、`CODING_STANDARDS.md`、README、架构文档和语言/工具配置。嵌套目录规则优先于根规则；仓库明示约定优先于下面的通用坏味道提示。

## 审查标准

### 规范（Standards）

报告可由代码审查发现、且自动化工具未必会拦截的实质问题。优先检查：

- 已记录约定是否被违反；每项必须引用规则文件和具体要求。
- 新旧行为的边界、错误处理、资源释放、并发与数据完整性是否被破坏。
- 输入、权限、敏感信息、注入面和不安全默认值是否引入风险。
- 变更是否引入难以维护的重复、误导性命名、数据团、原始类型滥用、重复分支、过度抽象或无必要的中转层。
- 测试是否覆盖本变更新增或修改的关键行为；只在现有测试策略或风险明确要求时将缺测试报为问题。

坏味道只是判断提示，不是硬性违规。若仓库规范、已有模式或需求明确接受该取舍，不要报告。也不要重复报告格式化、lint、类型检查或 CI 已可靠强制的纯工具问题。

### 需求（Spec）

逐条核对可用需求，寻找：

- 缺失、部分实现或行为与需求不符；
- 看似实现但在边界条件、错误路径或数据流中不正确的内容；
- 没有需求依据的行为、API、配置或抽象扩张。

需求不明确时明确不确定性，不把合理的实现选择伪装成缺陷。没有可用需求说明时跳过本轴，不以猜测代替审查。

## 输出报告

按下面结构输出，保持两轴分离；同一根因只放在最能解释它的一轴，并可在另一轴交叉引用。

```markdown
## 审查范围
- 基线：<fixed point 或未提交改动范围>
- 提交：<commit 列表或“未提交”>
- 需求来源：<路径、链接或“无可用需求说明”>
- 规范来源：<实际读取的文件>

## Standards
- [P1] `path/to/file:42`：<问题标题>
  - 证据：<代码事实；仅在违反已记录规范时引用规则文件:行号>
  - 影响：<可观察后果>
  - 建议：<最小修复方向>

## Spec
- [P1] `path/to/file:42`：<问题标题>
  - 证据：<需求文件:行号与代码事实>
  - 影响：<与需求的偏差>
  - 建议：<最小修复方向>

## 结论
- Standards：<N> 项；最高优先级 <P?> 或“无”。
- Spec：<N> 项，或“因无可用需求说明而跳过”。
```

优先级按实际影响标注：`P0` 阻断或可导致严重数据/安全事故，`P1` 高概率功能错误或明显回归，`P2` 应在合并前处理的质量问题，`P3` 可选改进。每项必须有可验证的文件位置、证据和影响；没有此证据就不要报告。没有问题时在对应标题下写“未发现需要行动的问题”。

不要把摘要、泛泛表扬、纯风格偏好或未复核的猜测当成 finding。若 diff 含令牌、私钥、连接串或个人数据，不要在报告中复述原值；只报告文件位置、敏感信息类型和脱敏证据。审查结束时说明未能验证的表面及原因。
