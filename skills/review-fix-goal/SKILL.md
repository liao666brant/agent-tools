# Review Fix Goal

把用户指定范围内的“审查、修复、复审、提交、推送”执行到可验证的完成条件。本技能自带审查和中文提交能力，不加载或调用其他 skill、子代理或特定宿主的专属工作流。

## 目标与预检

1. 确认当前目录是 Git 仓库。记录开始时的 `HEAD`、当前分支、用户指定的文件或目录、需求来源、验证要求和初始 `git status --short`。
2. 用户提供 commit、分支或 tag 时，将其作为不可信输入，通过参数边界解析成不可变 commit SHA；未提供时以开始时的 `HEAD` 作为 fixed point。后续每轮都使用同一 fixed point。
3. 保留范围外和任务开始后出现的用户改动，不修改、不暂存、不提交。完成条件是：没有经核实且仍需行动的 finding；相关验证通过；存在交付变更时已提交并普通推送。没有需求说明时可跳过 Spec 审查，但必须披露。

优先使用宿主暴露的持久 goal 能力来创建、恢复和完成上述条件；已有无关 goal 时不要覆盖。宿主只有 task/todo 时用同一条件跟踪进度，并说明它不保证跨回合自动续跑；两者都没有时在当前会话维护 finding 清单，不伪造原生 goal 状态。只有用户明确给出预算时才设置预算。

## 分支与授权

首次审查是只读操作，可以在当前分支完成。需要修复或提交时，在第一次编辑前确定当前分支和默认分支：优先使用当前 upstream 的 remote HEAD，其次使用唯一可解析的 remote HEAD；只在没有远端线索时根据本地 `main` 或 `master` 判断。无法可靠确定或处于 detached HEAD 时，不要猜测，向用户确认。

如果当前是默认分支且本次有变更要交付，先展示拟创建的分支名和影响并按当前环境规则取得确认，再创建体现修复范围的工作分支；已有工作分支则继续使用当前分支。不要为零变更创建空分支。

## 修复循环

开始首轮审查前，完整读取 [references/review.md](references/review.md)，后续每轮复用其中的范围、证据和判定规则。

1. 对 fixed point 到当前完整工作树执行首轮内建审查并建立 finding 清单。
2. 逐项复核，只做范围内的最小根因修复。
3. 运行与改动匹配的测试、类型检查、lint 或构建；区分本次回归和既有失败，本次回归必须修复。
4. 使用同一 fixed point 对当前完整工作树重新执行内建审查。
5. 仍有经核实的 P0-P3 finding 时继续循环；无效 finding 必须用证据关闭，不能用降级、backlog 或口头豁免代替清零。

不要在修复循环中提交。若同一根因连续三轮采用不同修复仍然出现，或修复需要扩大范围、执行破坏性操作、取得秘密或由用户作产品决策，停止试错并提出一个精确问题；仅在宿主允许时标记为 blocked。

## 交付

审查 clean、验证通过且存在交付变更时，完整读取 [references/commit.md](references/commit.md)，按其中规则完成授权、中文提交、提交后复审和普通推送。提交后的复审继续使用已加载的 [references/review.md](references/review.md)；若发现新 finding，回到修复循环。

没有可提交变更时不创建分支、空提交或无意义推送；其余完成条件成立即可结束。最终报告审查范围、finding 关闭情况、验证结果、提交、分支、远端，以及未验证或 Spec 跳过的内容。
