# 变更范围控制

每项变更都有一个正确大小，由用户请求定义。做多和做少都是没有定位边界的失败：前者把未请求改动带入审查或生产，后者由用户在使用时发现。先定位边界，再在边界内彻底完成，并在边界外保持不动。

任务中途若修正了边界，交付物应如同修正后的范围从一开始就是唯一范围。不要在标题、注释或理由中保留已放弃的选项；这些内容会重新引入已删除的超范围信息。

## 边界之外

- **不扩展未请求的行为或表面。** 用户点名某个层或文件通常是在描述目标；为达成该目标而必需的直接依赖可以修改，但相邻的独立问题应报告而非顺手修复。分离观察成本很低，纠缠的 diff 成本很高。
  *反例：用户要求让后端端点适配既有注册表单，Agent 又重设计了表单，审查者不得不先拆开两项改动。*
- **兼容性有成本，必须先证明有人在承担这项成本。** 迁移、双读路径、废弃别名和版本垫片只在真实用户、外部消费者或已存在的旧状态依赖它们时才成立。先确认事实；没有旧契约时，干净切换通常更小。
  *反例：尚未发布、没有安装用户的产品加入了保存格式迁移路径，维护和测试了从未有人写出的数据。*
- **复用既有实现，不要并列新增第二套。** 项目已存在渲染、格式化或业务路径时，在该路径上扩展。看似正确的平行实现会静默分叉，且通常没有测试会及时发现。
  *反例：新促销横幅在既有升级横幅旁从零实现；一个版本后只有其中一个获得新动画。*
- **优先修改既有规则，而非在旁边添加新规则。** 与被替换规则共存的新常量、开关或分支会形成两个事实来源，并把需要推理的状态翻倍。
  *反例：限制升级到单一分支的请求被实现为第二个规则常量；实际只需收窄原常量的含义。*
- **解决已陈述的问题，不要解决其泛化形式。** 扩展点、插件层和配置面应在存在第二个调用方时再建立，而不是因为想象中可能会需要。除非用户明确要求泛化，否则简单实现就是交付物。

## 边界之内

- **在行为隐含的每一处应用变更。** 请求的行为而非首次打开的文件才是工作单元。完成前，使用项目中适用的文本、结构或引用搜索检查同类项：同类卡片、同一键的本地化文本、同一帮助函数的其他调用方。逐一确认它们已变更或确实无需变更。
  *反例：新卡片类型缺少所有同类标签都有的分类前缀，界面因而把它显示成另一类对象。*
- **匹配同类项是请求的一部分，不是额外范围。** 既有类型的新成员会继承必填字段、命名惯例、层级元数据和文本惯例。只有值确实无法确定时才提问，不要遗漏同类项必需字段。
  *反例：新实体缺少所有同类实体均声明的稀有度字段，按稀有度分组的加载器静默丢弃了它。*

## 边界不清时

- **只询问会实质改变边界的选择。** 若不做用户尚未决定的关键选择就无法确定边界，应在跨越前提问。日常实现决策仍由 Agent 负责，不应变成确认关卡。

## 工作顺序

- **行为稳定后再锁定验证。** 不要为仍在讨论的逻辑过早编写测试或文档，它们会固定错误行为并增加返工。行为确定后，依据项目现有测试策略和风险，为关键成功路径、失败边界或不易人工验证的行为补充最小验证。
