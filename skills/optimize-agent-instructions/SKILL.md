# 优化 Agent 指令

优化既有指令的表达、组织和执行负担。以功能完整、触发准确、步骤可执行为准；篇幅或 token 变化只作描述，不能替代效果证据。

## 核对目标与基线

先确定用户要求的是只读审计还是落地修改，沿用本次会话已经明确的范围和授权。批量任务列出全部目标，逐项记录已核对、已修改或保留的状态。

区分可维护源码与生成或安装镜像，依据仓库说明判断，不按目录名猜测。修改源码及其必要入口；任务包含安装或同步时才更新对应镜像。

以用户说明和任务开始时认可的文本建立基线。已有未提交改动属于当前上下文，不能直接用 Git HEAD 覆盖；需要回看旧版本时先明确比较对象。读取目标正文，按受影响分支加载参考资料、调用策略和实际来源。

对每个目标核对以下契约，并区分原有约定与用户明确要求改变的部分：

- **用途与触发**：服务什么任务，何时主动调用，何时仅显式调用，哪些相邻任务不适用。根据用户说明、正文职责和实际使用证据，区分有效使用场景与过宽、误写或失效的触发措辞。
- **输入与输出**：接受的输入形式、默认选择、必须交付的内容与格式。
- **范围与执行**：根或模块范围、宿主与运行环境、执行分工、授权及副作用边界。
- **完成与恢复**：验证要求、评分含义、交付终点、失败处理及续扫断点。

原意存在实质冲突且证据无法判定时，保留该部分并指出待定选择，继续处理其他已明确的目标。

## 判定改动性质

| 改动 | 处理 |
| --- | --- |
| 表达或组织优化 | 合并同义规则、删除无决策价值的重复、按分支拆分；保持上述契约等价 |
| 有证据的缺陷修复 | 用实际反例、调用行为或来源证明偏离了已确认的职责，修复目标指令及必要的引用、元数据或辅助脚本，并验证相关边界；不扩展到普通业务代码 |
| 功能或政策变化 | 只有用户要求覆盖时才实施；不能作为精简的附带结果 |

纠正超出已确认职责的触发措辞，不等于关闭自动发现。取消有效场景、将其自动调用改为显式调用、删减输出小节、调整默认范围、取消执行分工、改变评分权重或放宽完成条件，都属于契约变化。新的模型、文章或通用最佳实践是核对线索，不自动决定这些政策。

## 优化表达与组织

- 保留改变 Agent 决策的领域知识、真实约束和易错边界，删除同义重复与已失效的说明。
- 结合已知目标模型、贡献者环境及执行证据，复查旧模型需要的手把手说明和常识性鼓励。可用代表性任务判断删减后是否仍满足原契约；共享指令兼顾实际使用者，特定模型才需要的指导按需提供，能力未知时保留关键约束。
- 多种方法都能满足约束时，写清结果和选择依据。只有顺序影响正确性、权限或恢复能力时才保留固定步骤；移除机械配方时仍保留其完成条件。
- 所有分支都需要的内容留在入口，独立分支的细节按需下沉。每个指针说明何时读取；简单内容保持单文件，不按行数强制拆分。
- 同一事实在合适位置维护，其他位置保留有条件的指针。拆分后验证独立安装仍能找到资源，不依赖个人路径或未声明的外部技能。
- 按已声明的运行环境检查真实能力。专用环境不附加不存在的跨宿主前提；工具不匹配时适配调用方式，保留原任务能力，不编造可用模型、参数或回退。

### Skill

批量审计时，在任务范围内区分可安装清单与实际启用的技能，检查名称和 description 的累计负担、触发竞争及相互矛盾。结合宿主实际呈现的内容核实是否发生描述截短；无法观察时注明限制，不设通用数量或 token 上限。

压缩 description 中的执行细节和同义词，保留符合已确认职责的独立触发分支，包括开发过程中应主动触发的情形。核对 description、正文、宿主调用策略和目录介绍是否一致。

多个技能覆盖同一请求时，按已确认的职责消除泛化措辞和冲突，保留有效场景的独立触发分支。合并、停用、卸载或调整默认入口须由任务授权覆盖，不能仅为减少数量而实施。脚本只承担有明确重复需求或可靠性收益的确定性工作。

### AGENTS.md 与 CLAUDE.md

先识别文档承担的职责：项目约定、模块索引、架构检索、运行入口或维护状态。保留仍在使用的索引、层级、兼容导入和恢复数据，不把索引文档直接改成规则清单。

将与任务无关的整仓必读要求改成带条件的来源指针。根级放共享约定和模块入口，模块级保留自身差异；遵守项目已有的索引范围，不自动扩建或裁掉层级。代码变化需要同步索引这一触发也须保留。

## 授权与完成边界

按真实风险和现有验收承诺选择验证。复用仍覆盖当前输入与环境的成功结果；输入变化或证据不足时补充相关检查，避免把测试鼓励变成每轮全量重跑。

按现有授权区分可连续执行的动作和需用户决定的边界。对经核实且已授权的工作流，写明安全依据及可连续执行的动作，例如使用一次性夹具、无生产访问的本地测试，可运行、修复本次改动造成的失败并复测。保留用户明确要求的确认点；调整这些确认点属于政策变化。

把目标工作流的完成条件写成可观察结果：需要交付可用实现时，包含运行、检查结果、修复本次变更造成的问题和复验；核对首版后等待审阅是否符合现有授权与用户要求，按前述改动性质处理。探索与重试应有范围和终点，达成结果、遇到真实阻塞或触及授权边界时停止相应分支。

## 验证与交付

把改后的文本逐项对照基线：每个有效使用场景的触发方式、输入形式、输出、完成条件和恢复分支，均应在新结构中找到对应位置；分别说明纠正的误触发及其依据、用户授权的契约变化。批量任务同时核对技能之间的发现与调用关系。

用代表性原始任务检查是否仍会触发、执行到同一终点，并覆盖本次修改影响的边界。复杂或容易漂移的流程可在隔离目录做独立前向验证，提供原始任务和必要材料，不预先告诉评估者期望结论。

检查 frontmatter、引用与锚点、调用策略、目录登记和补丁。仅改文档不运行无关构建；修改脚本时验证其实际行为。静态检查与场景推演不等同于跨宿主实测，结果中写明实际覆盖。

交付实际修改、保留的契约、验证证据和待定项。没有足够理由修改时保留原文并说明依据；仅在用户需要报告时另建报告产物。
