# UX 文案与文档

用户可见文本也是产品行为，应达到与代码相同的质量标准。以下规则适用于任何支持 Agent Skills 的宿主；不依赖特定 Agent、工具或平台。拿不准时，以刚遇到问题的用户身份重新阅读输出。

## 状态输出与诊断

- **报告生效值，而非存储值。** 状态展示应回答“现在运行会发生什么”。按运行时的实际规则解析环境变量和分层配置。
  *反例：配置查看器显示“未设置 API 密钥”，但环境变量中的密钥会在下一次运行时生效。*
- **诊断在失败时仍须真实。** 某一层配置无法加载时，使用仍可加载的最完整状态，不要退回空默认值。错误诊断比中止更糟。
  *反例：项目级配置损坏后，诊断命令改查空默认值，并错误报告缺少实际上已配置的 API 密钥。*
- **展示差异，不要倾倒全部内容。** 健康检查或诊断只列出偏离项及其来源；完整列表属于专门的查看命令。
  *反例：诊断命令输出十五行“字段：来源”，大多数都是“全局”。改为一行列出两个实际覆盖项。*
- **注释粒度与声明一致。** 组合值中只有部分来自不同来源或处于不同状态时，只标注该部分，不要重标整个组合。
  *反例：环境变量注入的 API 密钥让整个端点块被标为“（环境变量）”，尽管 URL 和模型仍来自文件。*
- **添加元数据后重读相邻标签。** 新后缀可能与既有值标签重复。
  *反例：“嵌入维度：默认（默认）”，应将值改称“自动”。*
- **机器可读输出是契约。** Porcelain、TSV、JSON 等输出不得加入装饰、提示或注解；信息应进入 stderr 或人类可读路径。缺失也是契约的一部分，应测试不应出现的内容。
- **不要截断载荷。** 诊断中的路径、ID、URL 必须能在窄终端完整复制；对这些行禁用自动裁切或省略。

## 错误信息

每条错误都应回答三件事：发生了什么、发生在哪里、下一步该做什么。优先指出出错文件或输入、被拒绝字段、允许字段，以及被拒绝设置应放置的位置。宁可明确失败，也不要静默降级；若仅为抑制堆栈而捕获异常，保留原始错误信息。

## 文档

- **每份文档只承担一项职责，由职责决定内容归属。** 页面可以是长期契约、提案、调查、待办、带日期的工作单或运行手册，但不应同时承担多种角色。事实应放在职责对应的唯一规范页，其他页面通过精确链接到达，而不是各自保留不完整复述。当两页都自称详细规范时，范围更广者保留共同规则，范围更窄者只保留自身增量。
  *反例：实现计划在上线后仍是事实规范，规则分散在计划和架构文档中；将稳定规则收敛到契约页、把步骤留在 Git 历史中后，读者只需信任一页。*
- **理由属于独立文体。** 操作指南说明如何执行，参考文档说明现状，设计取舍应进入设计记录、ADR 或作出决定的 PR。把“为什么”塞进使用页会把步骤推到后面，而且理由最先过期。一次性问答应留在答复中，而非永久文档。
  *反例：安装指南第二段解释为何选择某个队列；队列被替换后，段落却继续为旧选择辩护。*
- **每个事实只有一个规范来源。** 一同变化的细节（字段列表、优先级链、支持值）只放在一篇文档；其他位置链接过去。独立分发的产物（如随包发布的技能文件）和特定表面的补充说明可以合理复制。
  *反例：七字段白名单被粘贴到五份文档。*
- **复述后再链接不是周全，而是缺陷。** 一段内容若已经复制完整契约、结尾又写“完整说明见 X”，就删除复制内容，仅保留链接和该页面特有部分。
- **优先最小充分修改。** 修订既有文本时保留未受影响的措辞、结构和理由。移除真实重复，但不要无故改写邻近段落或压缩掉有价值的区分。
  *反例：把一个必需工作流改成可选时重写了多段邻近文本，随后又过度删掉了必要上下文；少量局部修改即可。*
- **插入内容必须尊重相邻关系。** 新增章节前先确认相邻段落的依附关系。
  *反例：新章节插在参数表与其输出格式脚注之间，使脚注脱离原章节。*
- **形容词需要证据。** “推荐”“更快”“更好”等判断必须来自自身基准或评估，而非乐观推测。
  *反例：功能注释称“推荐”，但项目评估显示其在强模型上不如默认方案，应称为“可选”。*
- **README 的每个章节只做一件事。** 定位章节不累积功能列表，快速开始不解释架构。README 保持精简并链接到文档；细节不断堆入 README 通常说明它离开了规范来源。
- **按读者先需要的内容排序；页面不再服务单一任务时就拆分。** 先写范围和权威入口，再写通用规则与主路径，最后才是例外、恢复和变更检查。概览层只总结稳定语义并向下链接，不为“自包含”塞入字段表、完整载荷或当前数值。拆分后保留一行用途和链接，而非第二份事实副本。
  *反例：入门页先给出完整参数参考，首次使用者需要的三条命令反而在两屏之后。*
- **提醒只点出最容易遗漏的一项。** 罗列所有产物会成为噪音而被整体跳过。
  *示例：“更新受此变更影响的文档；最容易遗漏的是随包技能文件。”*

## 易过期事实

文档按人的节奏修改，有些事实却会随提交、部署或重启变化。把这类事实写入长期页面会让页面自行变错。应记录从哪里读取当前答案，而非手工记录答案本身。

- **不要快照变化快于文档的值。** README、架构说明、运行手册和领域文档应承载意图、不变量、边界、流程和失败处理。版本与协议号、镜像标签、构建 ID、已部署提交、对象或迁移数量、过期日期，以及“当前已上线/尚未发布”等声明，应放入变更日志、Git 历史或发布工单。确需显示当前值时，从权威来源构建时生成。
  *反例：运行手册写着“生产环境当前运行 2.3.1”；四个版本后值已过期，值班人员据此查了错误版本的变更日志。*
- **指针应指向符号，而非仓库。** 事实的规范来源常在代码中；文档应给出具体文件及可搜索的符号、函数、数据键或标题，而不是写“见源码”、链接仓库根目录或目录。若没有单一符号拥有事实，这是代码边界问题，不应用复制表格掩盖。目录仅在事实来自有序文件集或加载器枚举的目录时可作为目标，且仍需给出可搜索的选择键。
  *反例：“协议版本定义在网络层”迫使读者搜索六个文件；应直接指向 `net/constants.py` 中的 `PROTOCOL_VERSION`。*
- **文档无法观察运行时。** 仓库只能说明某个提交意图如何运行；只有运行系统知道哪个提交在线、是否健康、实际服务哪个产物。文档应记录查询这些问题的命令或控制台，而非答案；合并不等于已部署。成功部署的证据应留在该发布工单中。
  *反例：手工维护“当前环境”服务版本表，直到某次部署后未更新，且 CI 无从发现。*

## 写最终状态，而非生产过程

产物会被未参与原始讨论的人阅读。只在当时会话中成立的内容，例如已放弃的方案、被纠正的范围或临时指令，对后来读者是噪音，甚至会被误解为产品声明。判断标准是：从未见过该讨论的读者能否理解这句话。

- **说明代码做什么，而非它曾接近做什么。** 标题、摘要和注释描述最终行为；中间尝试、放弃方案和负向范围留在讨论、Git 历史和审查线程中。
  *反例：PR 标题为“添加导出按钮（不含批量下载面板）”，读者必须先理解一个从未存在的面板。*
- **注释只承载无法从代码恢复的原因。** 值得写下的是顺序要求、上游缺陷或平台特性等非显而易见约束。只有当读者本来会考虑替代方案时，才解释“为什么不用 X”；不要重述代码显然的行为或为没人会选择的方案辩护。
  *反例：帮助函数保留八行“为何不缓存”的说明；两次重构后，那段文字成了唯一残留的历史。*
- **证据服务读者的决策，不服务作者的疑虑。** “更快”“默认安全”“应选此方案”等需要读者据此行动的主张应给出依据。单纯说明代码做什么不需要论证；过时的基准数字常比没有数字更误导。
  *反例：配置页以两大版本前的“快 40%”基准为默认值辩护，而被测路径早已不存在。*
- **交付物不叙述自身的制作过程。** 生成的报告、演示文稿、导出和界面是产品内容，应传达结论、值和说明，而非作者的实现笔记、方法理由或下一步。例外仅限本身就是帮助文本、空状态或明确要求记录方法论的文档。
  *反例：状态演示文稿在数据前先出现“本报告的方法与下一步”。*

## 行为变更后的同步检查

行为变更只有在所有文案位置一致时才算完成。按以下顺序搜索旧措辞：

1. `--help` 参数说明，最容易遗漏；
2. 集中式消息或字符串模块，以及命令文档字符串；
3. README 与其他文档页；
4. 随包技能文件、插件元数据、MCP 工具描述；这些同样是面向 Agent 的 UX；
5. 描述旧行为的路线图或状态说明。

再解析受影响链接：重命名标题会破坏锚点，移动文件会破坏相对路径，而常规测试通常不会报告这些问题。

## 测试文案

- 断言扁平化后的文本或行为，而非控制台排版；测试运行器通常按约 80 列换行。可使用 `" ".join(output.split())` 后再断言子串。
- 运行测试时清除 `FORCE_COLOR` 和 `COLORTERM`，避免调用环境让富文本控制台在捕获输出中写入 ANSI 转义序列。
- 对机器格式除了断言必须存在的内容，也要断言不应出现的内容。
