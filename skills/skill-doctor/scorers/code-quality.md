**评分标准**

本评分器适用于 Agent 产生了代码改动的会话。评估实际代码产物，即改动本身，而不是生成它的过程。以目标仓库已经建立的约定为标准，像谨慎的资深审查者审查同一拉取请求那样判断。结论是二元的：`approve` 表示审查者会原样合并，至多提出微不足道的小建议；如果审查者会坚持合并前修复，即使只有一个真实缺陷，也应判为 `block`。若精简会话没有展示足够改动，结论为 `insufficient_evidence`，并从汇总中排除该会话。以下条目是常见质量维度，并非穷尽清单；任何低于谨慎资深工程师交付标准的问题都应纳入判断。

评估：

- **设计。** 改动形态适合该代码库；不存在过早抽象、范围蔓延，或本应归属于其他位置的改动，例如库、配置值或独立服务。
- **正确性。** 改动实现其声称的行为，包括 nil 或空输入、边界等情况，以及并发安全，例如竞态、不安全共享状态、生命周期超过请求作用域值的派生任务。
- **复杂度。** 函数、类型和表达式都没有承担超出需要的工作；未为尚不存在的需求加入推测性泛化或间接层。
- **仓库约定。** 与同一包或模块中的相似代码采用相同惯例，包括错误处理、类型位置、命名规则及周边代码显示的其他既有模式。即使新代码可以运行，无解释地偏离明确的本地模式仍是缺陷。
- **代码异味。** 包括没有具名常量的魔法数字或字符串、本应提取共享函数的复制粘贴、被注释掉的代码、含糊或过期的 TODO、只修补症状而非根因的变通、静默吞错，以及本可用提前返回压平的深层嵌套。
- **测试。** 改动应有测试，且测试真实验证其声称的行为，错误实现会导致测试失败；不能只断言琐事或通过 mock 绕过受测逻辑。测试应覆盖错误和边界路径，而不仅是正常路径；也不能过度耦合内部实现，以免无关改动导致失败。
- **命名。** 每个新标识符都准确表达其含义，长度足够消除歧义但不过度冗长。
- **注释。** 解释原因而非复述行为；导出符号的文档注释应描述用途和约束，不叙述实现；注释描述最终状态，不记录编辑过程、重构过程或旧状态。
- **差异卫生。** 改动只包含拟提交内容，不混入临时文本、草稿脚本、调试输出或其他验证脚手架。
- **文档。** 若改动影响软件的构建、测试或使用方式，应在同一改动中更新 README、指南或 API 文档。
- **纠正。** 用户在会话中指出的缺陷，无论最终是否修复，都应计入产物评价；需要外部纠正本身就是负面信号，而不只是未解决缺陷才算。

不在本评分范围内：Agent 的工作路径是否直接，这由效率评分器评估；以及它是否遵循指令或技能。只按产物本身判断。

**理由**

用 1 至 3 句话指出决定评分的具体文件、模式或缺陷，引用或紧密转述相关代码行或约定。说明什么本可发现该问题，例如 lint 规则、Agent 应搜索的仓库约定、测试用例或技能。若结论为 `insufficient_evidence`，说明缺少什么，例如没有生成差异，或差异未出现在会话中。
